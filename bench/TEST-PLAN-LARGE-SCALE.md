# 中等 → 大规模对比测试计划（GitMono vs git）

> v1 2026-09-29。目标不是"再跑一遍基准"，而是**判断 mega2+ScorpioFS 相对 git 是否具备明显优势，值不值得投入大规模测试**。
> 因此本计划的核心是一套**成功判据**和一个**规模闸门**：中等规模不达标就不做大规模。

---

## 1. 先明确「明显优势」的判据

前几轮实测已经说明一件事：**优势不是全面的**。同一棵 20k 树、服务端在另一个节点：

| 指标 | git | mono | 谁赢 |
|---|---|---|---|
| 拿到可工作副本（就绪） | 62.2 s | **1.04 s** | **mono 60×** |
| 工作区磁盘 | 整棵树 | 按需 + 一个 revision | **mono** |
| `status`（本地 clone） | **218 ms** | 552 ms | git 2.5× |
| 多工作区 | 每份完整拷贝 | chain fork ≈ 4 KB | **mono** |

所以判据必须**按指标分类**，不能用一句"更快"概括：

**S1（必须达标）就绪时间**：`worktree add` ÷ `git clone` **≤ 0.1**（即 mono 至少快 10×），
且该比值**随树规模不恶化**（这是"不物化"的直接推论）。

**S2（必须达标）多工作区成本**：N=5 工作区时，
mono 的真实落盘增量 ÷ git 的落盘增量 **≤ 0.2**，
且 mono 的创建时间**不随已有工作区数量增长**（chain fork 是零拷贝改名）。

**S3（必须达标）磁盘效率**：单工作区真实落盘，mono ≤ git 的 0.5。

**S4（观察项，不作门槛）**：`status` / `add` / `commit` / `push` 的逐项对比。
mono 目前 status 常数约 0.55 s，在本地盘上打不过 git；**如实记录，不粉饰**。

**闸门规则**：中等规模下 **S1、S2、S3 全部达标** → 才进入大规模。
任一不达标 → 先查是"实现常数"还是"架构问题"，修正后重测，不直接放大规模。

> 为什么要这个闸门：大规模测试的成本不是线性的（播种要分批推送、mega2 对象存储在大树下有稳定性风险——本机 124k 树曾把 rustfs 拖到 2.9 GB RSS 并开始返回 500）。先在中等规模确认结论，再放大。

## 2. 规模阶梯

| 档 | 文件数 | 树大小（估） | 用途 |
|---|---|---|---|
| S（已做） | 20k | ~10 MB | 打通链路（已完成，见 `ACK-REMOTE-WORKTREE-2026-09-29.md`）|
| **L（本次，跳过 M）** | **500k** | ~250 MB | **主判据在此判定**；一次到位，不做中间档 |
| XL（可选） | 1M+ | ~600 MB+ | 只在 L 达标且需要对外结论时做 |

**为什么直接 L**：M 档的结论（就绪时间比值、chain fork 是否零拷贝）在 S 档已经显出方向，
而 M 的**播种成本与 L 同量级地受同一个瓶颈支配**——所以中间档只会多花一次集群时间的钱，
不增加信息量。直接 L，把预算花在真正的规模上。

**「一切都放在一个仓库里」**（用户要求，也是本计划的设计约束）：

- **mega2 侧**：`/project` 这一个 monorepo。
- **git 侧**：**同一个 mega2 的 git 端点**（`git clone <M2>/project`）——
  两侧读**同一份存储**，服务端变量归零，只比客户端取数方式。
- 因此**不再单独搭 Gitea**：那需要第二个 500k 仓库（播种成本翻倍），
  且违背"一个仓库"。代价是 git 侧的绝对数字含 mega2 的 git 协议实现，
  这一点必须在报告里写明（诚实边界）。

**为什么 L 定在 500k**：本机已在 124k 上取得完整数据（四项修复的 before/after）。
500k 是 124k 的 4 倍，足以验证"S1 的比值不随规模恶化"这条最关键的结构性主张。

## 3. 拓扑与环境

**两侧共用同一个服务端存储**是这套对比的关键设计（服务端变量归零）。

```
        ┌─────────────────── ACK 集群 ───────────────────┐
        │  node A                        node B          │
        │  ┌──────────┐                 ┌─────────────┐  │
        │  │  mega2   │◄── 跨节点 ──────│ bench pod   │  │
        │  │ postgres │                 │ (libra +    │  │
        │  │ redis    │                 │  scorpio    │  │
        │  │ rustfs   │                 │  daemon)    │  │
        │  └──────────┘                 └─────────────┘  │
        │        podAntiAffinity 强制分节点                │
        └────────────────────────────────────────────────┘
```

- **强制跨节点**：bench pod 用 `podAntiAffinity` 对 `app: mega2`；已验证生效。
- **节点规格**：mega2 所在节点需容纳 postgres+redis+rustfs+mega2（≈2.5 GiB）+ 大树的元数据；
  bench 节点需容纳 daemon + 工作区 + git clone。
  - M 档：2 × `ecs.e-c1m2.xlarge`（4c8g）足够（20k 已跑通）
  - L/XL 档：mega2 节点升到 `ecs.e-c1m2.2xlarge`（8c16g），bench 节点保持 4c8g 或同步升
- **镜像**：`v0.3.0-ack-libra`（daemon 来自 `bench/gitmono-vs-git` + 本轮修复过的 libra + git + python3）。
  **每次测新代码都要重建并重推**——并用 `strings`/`md5` 核对，不要相信"大小相同就是同一个"（这个坑踩过）。

## 4. 测试矩阵

每个规模档跑完整矩阵；每格 ≥3 轮取中位数，记录 min/max。

### 4.1 就绪与规模（对应 S1）

| ID | git 侧 | mono 侧 |
|---|---|---|
| READY | `git clone <M2>/project` 完成且可读可写 | `libra worktree add --backend scorpiofs` 完成且可读可写 |
| DISK | `du -sb` clone 目录 | **真实落盘**：upper + sealed + store（**不要 `du -sb` FUSE 挂载点**，那是逻辑可见大小） |

### 4.2 多工作区（对应 S2）

| ID | git 侧 | mono 侧 |
|---|---|---|
| MULTI-5 | `git clone` + `git worktree add` ×5，测总耗时与总落盘 | `attach` + `libra fork` ×5（chain），测总耗时与真实落盘 |
| MULTI-10 | 同上 ×10（看 mono 是否仍是线性于 fork 数而非树大小） | 同上 |

### 4.3 日常操作（S4，观察项）

| ID | git 侧 | mono 侧 |
|---|---|---|
| STATUS | `git status`（本地 clone） | `libra status`（fast path） |
| STATUS-1F | 改 1 文件后 | 改 1 文件后 |
| ADD | `git add -A` | `libra add -A` |
| COMMIT | `git add/commit/push` | `libra sync` |
| SWITCH | `git checkout <branch>`（10% 变更） | `libra` refresh 到新 revision |
| READ | 100 随机文件冷/热读 | 同 100 文件（冷/热） |

### 4.4 规模斜率（贯穿，验证"不随规模恶化"）

把 S/M/L 三档的 READY 与 MULTI 画成曲线：
- 预期 **git 随规模线性上升**，**mono 基本水平**；
- **S1 的"不恶化"就由这条曲线证明**，而不是靠单点数字。

### 4.5 git 侧的两条对照线

| 线 | 形态 | 作用 |
|---|---|---|
| **主口径（本次唯一）** | `git clone <M2>/project` | 与 mono 侧读**同一份存储** → 只比客户端取数方式 |

> 原计划的第二条线（集群内 Gitea + `--filter=blob:none`）**本次不做**：它需要第二个
> 500k 文件的仓库，播种成本翻倍，且违背"所有规模都放在一个仓库里"的约束。
> 代价要写进报告：git 侧的绝对值包含 mega2 的 git 协议实现，**因此不能据此断言
> "git 本身慢"**；能断言的是"在这套存储上，两种取数方式的差距"。

### 4.6 观测工具（低开销，不干扰被测对象）

用户要求"确保测试后能拿到所有想要的性能指标，但不要太阻碍本身性能"。设计如下：

| 观测 | 手段 | 开销 |
|---|---|---|
| 进程 RSS / fd / CPU ticks / 线程数 | `sampler.sh` 每秒读一次 `/proc/<pid>/stat`、`/status`、`fd/` | 1 Hz，无 ptrace、无 perf，可忽略 |
| pod 级网络收发 | 同一采样器读 `/proc/net/dev`（非 lo 接口求和） | 同一次循环内 |
| 阶段对齐 | bench 脚本在每阶段前后写 `M <ts> <phase>` 标记 | 每阶段一次 |
| 指标落盘 | bench 脚本写 `R <ts> name=value` 机器可读行 | 每指标一次 |
| 服务端（mega2） | mega2 pod 加 **sampler sidecar** + `shareProcessNamespace: true`，才能读到 mega2 的 /proc | 同上，独立容器 |
| 采集通道 | 两者都打到 **stdout**，用 `kubectl logs` 收——不需要额外存储组件 | — |

**刻意不做的事**（会干扰测量）：
- 不装 Prometheus / cAdvisor / node-exporter（额外容器会抢 CPU、且引入网络开销）
- 不在被测目录里写任何东西（采样输出全在 `/tmp`）
- 不用 `strace`（会放大 FUSE 操作到失真——已踩过：`-f` 下 41 s 变 309 s）

**采样数据的用法**：`M` 标记把时间轴切成阶段，`S`/`N` 序列在阶段内取
峰值/均值。判据 S1/S2/S3 用的是**计时**，资源曲线用于**解释**（例如"commit 慢是因为
对象存储写放大"，而不是靠它下结论）。

## 5. 播种方案（这是最容易被低估的部分）

**教训（S 档实测）**：20k 文件推一次会失败——
`git push` 超过 `http.postBuffer`（默认 1 MiB）会改用 **chunked 传输**，服务端 hang up
（`the remote end hung up unexpectedly`，1.4 s 即失败）。修法：**调大 `http.postBuffer` + 分批推送**。

因此播种要：

1. **分批**：每批 ≤2000 文件；100k → 50 批。实测每批 23–50 s（批越大越慢、且呈上升趋势，说明服务端在大树上变慢）。
   - 100k 估**约 20–40 分钟**；500k 估**2–4 小时**。
2. **每档只播一次，结果复用**。不要每轮重播。
3. **播完必须校验**：再 clone 一次核对文件数与 tip，防止"推了一半"被当成完整树——**否则后面所有数字都是在残缺树上测的**（S 档第一轮就是这么废掉的：`/project` 只有 1 个文件，却照样出了"漂亮的"耗时）。
4. 树的形状要**有真实结构**（多级目录、每目录多文件），不要平铺——否则测不出目录遍历的代价。

## 6. 执行顺序

```
阶段 0  准备（不花钱）
  ├─ 重建并核验镜像（含本轮修复）→ 推 ACR
  ├─ 生成 M 档树（本地生成，避免占用集群时间）
  └─ dry-run 一遍 bench 脚本（本地容器、小 NFILES）

阶段 1  M 档（100k）— 约 2 小时集群时间 ≈ ¥4
  ├─ 起集群（2 节点）→ 播种（20–40 min）→ 跑矩阵（每项 3 轮）
  ├─ 跑第三方对照（Gitea + partial clone）
  └─ 判定 S1/S2/S3 → 达标则继续，否则停在这里分析

阶段 2  L 档（500k）— 只在 M 达标后做；约 6–10 小时 ≈ ¥15–25
  └─ 重点看斜率，不是绝对值

阶段 3  产物
  ├─ 原始 JSONL → results/raw/
  ├─ 结论文档 → results/
  └─ 网页更新 → brewfs 服务器 :8790
```

**每一步都可中断**：集群用完即删，判据不达标就不进下一档。

## 8. 测量陷阱清单（都真实踩过）

| 陷阱 | 后果 | 规避 |
|---|---|---|
| `du -sb` 量 FUSE 挂载点 | 得到**逻辑可见大小**（12 万文件的表观之和），比真实占用大 16 倍 | 只量 upper/sealed/store |
| `cold` 只清 OS page cache | 后几轮"cold"其实是"冷 page cache + 热 store" | 报告里写明只有首轮是真冷 |
| 容器内 `strings` 不存在 | grep 返回 0，被误读成"镜像旧" | **探针失败 ≠ 结果为否**；探测要在宿主机上做 |
| 用 git tip OID 当 revision | mega2 只认内部 monorepo OID → refresh 变空转 | 用 `latest-commit` 的返回值 |
| `--no-checkout` 的空工作区 | status 报"全部删除"、sync 忠实提交 → **曾误删 124,008 个文件** | 破坏性操作前断言"cwd 是活挂载 **且** 删除数低于阈值" |
| 播种后不校验 | 在残缺树上测出"漂亮"数字 | 播完必须 clone 回来核对文件数 |
