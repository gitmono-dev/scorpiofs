# R2：pack 生成 ~65 秒的根因：**对象存储饱和，不是服务端代码**（2026-09-30）

## 最终结论

**那 ~57 秒是 rustfs（对象存储）在打满 CPU，不是 mega2 的代码效率问题。**

```
rustfs 每 5 秒的 CPU 增量（4 核限额）：
  克隆期间 : 17–18 s   ← 用掉 3.5/4 核，饱和
  克隆结束 : 6 → 3 → 0 ← 立刻归零
```

550,013 个对象用 57 秒 = **约 9,650 对象/秒**，rustfs 在算哈希/校验/IO。

## 为什么这个结论可信

**它同时解释了此前所有互相矛盾的观察**：

| 观察 | 用"rustfs 饱和"解释 |
|---|---|
| 并发 64→1024 完全无效 | 更宽只会更深地压已饱和的下游 |
| server CPU 只有 1.4/4 核 | 服务端在等存储，不是算不过来 |
| git 全量 72.1 s ≈ mono 66.8 s | **两边打的是同一个天花板** |
| `open` 只占 0.137 s | 流是惰性的，真正的读取发生在 drain |

| 5 | 每 blob 两次拷贝的哈希 | ❌ **实测 1,100,026 次哈希总计 <1 ms** |

**第 5 次特别值得记**：我读到 `hash.rs:450` 里 `d.extend(data)` 那行时很确信 ——
"55 万次拷贝、162 µs/对象、流式替代方案就写在四行之上"。**全是错的**：
60 字节的 SHA-256 是亚微秒级，1,100,026 次合计 **< 1 毫秒**。

**能从源码读出来的东西，不能替代测量。** 前两次靠读码直接改代码，是方法错误；
后四次改成了先测量，每次都拿到有价值的**否定**结果，最后才收敛到真相。

## 对目标（GOAL-MONOREPO-WIN）的意义

**这 57 秒不该记在 mega2 头上。** 它是**测试环境的对象存储配置**：
rustfs 与 mega2 挤在**同一个节点**、各限 4 核，互相抢 CPU；
生产会用真 S3 且存储与计算分离。

因此：

1. **W4（全量 clone 可比）** 的剩余差距主要来自共享节点争抢，不是架构缺陷
2. 报告里必须写明：**本环境的对象存储是瓶颈，全量 clone 数字受其限制**
3. 若要继续压这 57 秒，方向是**环境**（分开部署 rustfs、提高其限额、换真 S3），
   而不是继续改 monoengine

## 附带成果（这些是真实的，不受本结论影响）

- **首字节 81.28 s → 0.0014 s**（消除静默，libra 的 60 s idle 超时不再触发）
- 树读取走 Redis 缓存（内容寻址，无需失效逻辑）
- fetch 宽度可配置（默认 64，替代写死的 16）
- 编码器 panic 不再消失（6 处调用点接住 `JoinHandle`）
- 哈希改为流式（顺带修掉 thread-local hash kind 的隐患）

  真正的对象存储往返发生在 drain 期间

## CPU 实测：两个假设都不完全成立

用容器 cgroup 的 `cpu.stat` 在一次 clone 前后取差：

```
before :  92,964,899 us
after  : 182,454,579 us
CPU    :  89.5 s
wall   :  64 s
限额   :  4 核（节点 8 核）
→ 平均 1.4 核在跑
```

**结论：既不是纯等待，也不是 CPU 饱和。**

| 假设 | 是否成立 |
|---|---|
| (a) 等待型 —— 池小钳住并发 | ❌ 89 秒 CPU 不可能是纯等待 |
| (b) CPU 饱和 —— 550k 次 sha256 打满 | ❌ 只用了 4 核里的 **1.4 核**，有余量 |

按 550,013 个对象折算：**104 µs 墙钟/对象、约 162 µs CPU/对象**。
这个量级**远超**小文件 SHA-256（约 5–20 µs），说明每个对象上有一大坨工作，
但**只占 35% 的 CPU 预算** → **存在一个尚未找到的串行点**，同时又有 CPU 余量。

**这解释了并发扫描为何完全无效**：并发上去了，但某个串行环节没有跟着放大。

## 下一步：用剖析器，不要再猜

CPU 有余量 + 并发无效 = 典型的"剖析器才能定位"的情形。具体路径：

1. **perf 剖析**服务端进程一次 clone，直接看 CPU 火焰图落在哪个函数
   （若是 `sha256`/`zlib` → 减少每对象工作量；若在锁/通道 → 找那个串行点）
2. 若无 `perf`（容器常缺），退而求其次：在 drain 循环内**逐段打点**
   （取流 / 拼装 / `Blob::from_content_bytes` / 发送），拿到子阶段分解
3. **在拿到剖析数据前不改任何代码**
