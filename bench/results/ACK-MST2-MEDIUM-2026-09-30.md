# ACK 中规模实测：mega2+ScorpioFS vs git（2026-09-30）

**规模**：50,000 文件单一 monorepo　**拓扑**：ACK 跨节点（`mega2` 在 `.89`，客户端在 `.90`）
**口径**：每项单次测量，非中位数（见"测量局限"）

---

## 结论（先说重要的）

**"mono 全面快于 git" 不成立，我不打算把它包装成成立。** 真实结论是**一个明确的取舍**：

| 维度 | 谁赢 | 差距 |
|---|---|---|
| **单工作区就绪（等深）** | **git** | 6.77 s vs 14.88 s，**git 快 2.2×** |
| **单工作区就绪（全量）** | 平手 | 72.1 s vs ~72 s（两边传同一批 55 万对象） |
| **5 个工作区的磁盘** | **mono** | 4.0 MB/视图 vs **~5 KB/视图**，**约 800×** |
| **5 个工作区的耗时** | **git** | 5.58 s vs 8.97 s，git 快 1.6× |

**mono 的架构优势在"多工作区"，不在"单工作区延迟"。** 单工作区上 git 更快，
因为 git 的 checkout 在 50k 规模下本来就很快，而 mono 的 attach 要把 MST/2 视图
投影成文件系统。但**第 N 个工作区**的成本结构完全不同：

- git：每个 worktree 都是**一份完整的 50,000 文件检出**（4.0 MB 真实落盘）
- mono：fork 是 upper 层的**零拷贝 rename**，lower 共享，**文件内容根本不落盘**
  （读时从 MST/2 拉取）

规模放大后这个差距是致命的：50 个工作区，git 要 200 MB，mono 要 250 KB。

## 必须先纠正的一个错误结论

**我此前报告的 W1 = 0.174「达标」是无效的**，已作废。

那个数字是 **全量 git（85.3 s）÷ shallow mono（14.9 s）** —— **两边口径不同，不可比**。
当时的动机是"mono 侧不 shallow 就失败"（服务端 81 s 静默触发 libra 的 60 s 超时），
但把失败方换成 shallow、另一方保持全量，得到的是一个没有意义的比值。

**等深与全量两种口径的真实数字**：

| 口径 | git | mono | 说明 |
|---|---|---|---|
| **都 `--depth 1`** | **6.77 s** | clone 9.58 s + attach 5.30 s = **14.88 s** | git 快 2.2× |
| **都全量** | 72.10 s | ~72 s（clone 后仍需 attach） | 平手，两边都传 55 万对象 |

我特意在目标文件里加的 **W4（不依赖 shallow 才能成立）** 就是为了堵住这个漏洞 ——
它生效了。

## W2 详细数据（多工作区）

```
基准（两侧都 depth 1，不计入）：
  git  .git        9,442,894 bytes
  mono 仓库        4,947,079 bytes

GIT：再加 5 个 worktree
  耗时            5,578 ms
  .git 增长       26,181,481 bytes
  工作树总计      20,029,205 bytes      （每视图 50,001 文件）

MONO：再加 5 个工作区
  耗时            8,966 ms
  每个挂载可见    50,000 文件 × 5       ← 门禁验证通过
  daemon upper    24,821 bytes          ← 这是真实落盘增量
  daemon sealed   4,096 bytes
  daemon store    363,987 bytes
```

**口径说明（两种都列，避免挑好看的报）**：

| 口径 | git | mono | 比值 |
|---|---|---|---|
| 每个视图**真实落盘** | 4,005,841 B | ~4,964 B（24,821 ÷ 5） | **0.0012** |
| 每个视图**呈现大小**（最保守） | 4,005,841 B | 643,035 B | **0.16** |

最保守口径 0.16 **仍 ≤ 0.2**，W2 通过。

**代价必须一起说**：mono 工作区的文件内容**不在本地**，读取要过网络。W2 省下的磁盘
是用读延迟换来的 —— 这一点在任何结论里都不能省略。

**门禁**：上一轮测量作废，因为它在**没有 `/dev/fuse` 的 tool pod** 里跑，
`worktree add` "成功"了但每个工作区只有 **3 个文件** —— 5.2 MB 的"工作区"其实是
daemon 内部状态。本轮在特权 pod 里跑，并**逐个校验挂载确实投影出 ≥40,000 文件**才采信。

## 服务端修复的实测效果（R1）

四项改动（并发可配、树走 Redis 缓存、删死查询、NAK 提前）部署后的实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `git-upload-pack` **首字节** | **81.28 s** | **0.0014 s** |
| `git-upload-pack` 总耗时 | 82.9 s | 66.8 s |
| libra 全量 clone（默认 60s 超时） | 失败 `error sending request` | 失败 **`error decoding response body`** |

**首字节的修复是决定性的**：服务端不再静默 81 秒。libra 的 60 s **idle** 超时
（只在无字节流动时触发）不再被触发 —— 现在失败的是**总时长**，不是静默。

**但总耗时只降了 16 秒**，而代码阅读预期的降幅要大得多。用服务端自己的 `time_it!`
计时定位后确认：耗时在**生产条目**（`receive batch: ~10.5s/批 × 5`），
编码本身只占 0.9 s/批。

**两次打偏的记录**（都是"读代码推断"而非实测导致）：
1. 先改了**消费端**并发（`try_for_each_concurrent`）—— 但它不控制读的并发
2. 再改了 **fetch 宽度**（`get_objects_stream` 里写死的 16）—— 改对了地方，
   但**总耗时没变**（66.8 s），说明还有第三个因素

第三个因素**尚未定位**。已知：pack 里 550,001 个 blob，编码只占 1 秒，
所以 ~65 秒花在把对象从存储搬到编码器。串行递归（`traverse` 的
`for t in trees { self.traverse(t).await }`）是嫌疑之一，但改它需要共享
`exist_objs` 去重集，**改错会导致 pack 内重复对象或 `process_index != object_number` panic**，
在没有实测证据前不动。

## 测量局限（会写进任何对外结论）

1. **单次测量**，非 ≥3 轮中位数 —— 集群噪声未量化
2. **一个规模**（50k），未做规模曲线
3. **D4/D5 未测**：多工作区只测了磁盘与耗时；`status`/`add`/`commit` 的对比只做过
   50k 上的 `status`（1.7 s），未与 git 并排
4. 所有 mono 数字**依赖 `--depth 1`** 才能与 git 的短耗时同框；全量口径下两者持平
5. 服务端仍有 ~65 s 未定位的 pack 生成本（见上），**这是 R2 的目标**

## 下一步（R2）

目标：定位那 ~65 秒。方法按"先测量后改动"：

1. 给 `traverse` 的每个阶段加计时（对象拉取 / 树读 / 发送），**先拿到分解**
2. 用分解结果决定是改串行递归、还是对象存储层、还是别的
3. **不基于代码阅读直接改** —— 本轮的两次打偏都源于此

**并且不再追求 W1（单工作区 ≤0.2×）** —— 等深口径下它数学上不可能达成，
双方需要的元数据量本就相同。W1 应改为"全量口径下不慢于 git"（当前持平）。
