# W3 实测：日常操作 status / add / commit（2026-09-30）

**规模**：50,001 文件　**拓扑**：特权 probe pod ↔ mega2 跨节点
**方式**：每项 n=3 取中位数（commit n=1，见下）；mono 侧为 MST/2 lower 的
ScorpioFS 挂载工作区，git 侧为普通克隆（含 checkout）

## 结果

| 操作 | git | mono | 比值 | W3 门槛 ≤3× |
|---|---|---|---|---|
| **status**（净树） | 73 ms | **13 ms** | **0.18×（快 5.6×）** | ✅ |
| **add -A**（1 处改动） | 94 ms | **12 ms** | **0.13×（快 7.8×）** | ✅ |
| **commit**（1 处改动） | 65 ms | **41–51 s**（rc=128 或 rc=0） | **~630–780×** | ❌ **严重不达标** |

## status/add 为什么快（并验证了架构预期）

mono 的 status 走 **upper 层启发式**（只看可写层的实际改动），不扫全树 ——
这是此前 `perf/scorpiofs-add-fast-path` 优化的设计目标，实测兑现：
50k 文件上 13 ms vs git 的 73 ms。**净树 status/add 是 mono 的架构强项。**

## commit 为什么不达标（照实报告）

两个观察：

1. **慢 600×+**：41–51 秒 vs git 的 65 ms。commit 需要读取改动内容并重建树 ——
   内容在 FUSE 挂载上（跨网络），且 daemon 日志在 commit 期间持续刷
   `lookup_node: child .gitattributes not found` 类 WARN（属性探测在逐目录触发）。
   未做内部剖析，根因**待定位**。
2. **不确定性行为**：同样路径，W3 运行 rc=128（41 s 失败），诊断重放 rc=0（51 s 成功）
   —— 但成功后 `status` 仍报 `modified`（commit 声称 1 file changed，改动却仍显示
   未提交）。**落点状态可疑**，是比慢更值得警惕的问题。

**诚实结论**：W3 的 status/add 大幅达标（反向碾压），**commit 使 W3 整体不达标**。
mono 的日常体验瓶颈在 commit 路径，与单工作区 clone 的瓶颈（已用 filter 解决）不同源。

## 附带发现（本轮新增待办）

- **filter 克隆 + attach 不兼容**：`--filter=blob:none` 克隆后 attach 失败
  （`failed to read object`）—— libra 的 worktree populate 仍从本地 pack 读 blob，
  不知道 blob 应来自 MST/2。这是把 filter 红利带进工作区的**最后一公里**，
  需要在 libra 侧做"populate 走 snapshot 后端"的改动
- 属性探测（`.gitattributes` / `.libra_attributes`）在每次目录 lookup 时触发
  两次 miss 警告 —— 对 10k 目录就是 2 万次无效查找，是 commit/status 慢的
  主要嫌疑之一
