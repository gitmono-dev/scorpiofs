# mega2 性能提升方案（2026-09-30）

## 数据基础（全部实测）

| 观察 | 数值 | 来源 |
|---|---|---|
| 一次全量 clone | ~65 s | 多次测量 |
| 其中 `drain`（读 blob 流+推入编码器） | **57.2 s / 99.8%** | per-directory 打点，10,479 目录 |
| `open`（拿到流） | 0.137 s | 同上 |
| `trees`（树读取） | **9 ms** | 同上 |
| 编码 | 0.9 s/批 | git-internal `time_it!` |
| 写出 | 0.07 s/批 | 同上 |
| 哈希（550k 次） | **< 1 ms** | 实测，否定了我的假设 |
| 对象总数（含历史） | 560,472 | 编码器断言 |
| blob 总数 | 550,013 | 打点 |
| rustfs CPU（clone 期间） | **3.5/4 核** | cgroup 采样 |
| git 全量 clone（同树） | 72.1 s | 对照 |
| **并发扫描 64→1024** | **56.0→56.5 s 无变化** | 实测 |

**结论：瓶颈是 550,013 次逐 blob 的对象存储往返。** 编码、哈希、树读取、并发全部不是。

## 为什么这是"要传的数据量"问题，而不是"并发"问题

同一个 tip，**只需要 50,000 个 blob**，但 pack 里装了 **550,013 个** ——
多出来的是已收缩祖先提交（`ac72fd39e3`，500k 文件种子）的树所引用的 blob。

git 同样传这 550k（72.1 s），所以**两边都在打 rustfs 的天花板**。
单靠调并发无法改善 —— 已被 16 倍扫描否定。

## 提升方案（按 收益÷风险 排序）

### ★ 方案 A：v0 增量协商（推荐，**不是新发明**）

**机制**：客户端发 `have <oid>` 声明自己已有哪些提交，服务端只发差额。
这正是 `incremental_pack(want, have)` 已有的能力 —— `have` 非空时它从
`have` 可达的树开始遍历，**跳过已有的对象**。

**实测支持**：`smart.rs:272` 的 else 分支（`have` 非空）**已经在调用
`incremental_pack(want, have)`**，实现完整、可用，只是 **libra 的 clone 从不发 `have`**。

**效果推算**：第二次 clone / 拉取时只传差异，而非 550k 个对象。

**为什么它不是"新发明"**：
- 服务端逻辑：`incremental_pack` 已实现（`monorepo.rs:512`）
- 协议路径：`smart.rs` 已按 `have` 是否为空分发
- 唯一缺口在**客户端是否发 `have`**（libra 侧），或是否用 `fetch` 而非全新 clone

**风险**：低。改动落在已被测试覆盖的既有分支上。

### ★ 方案 B：把 `filtered_pack` 接到 v0 路径（中等）

**机制**：`traverse_trees_only` **只读 tree、不读 blob**（已核实）。
`Monorepo::filtered_pack` 实现完整（`monorepo.rs`），
**但只有 v2 路径解析 `filter`**（`v2.rs:142`），而 libra 讲 v0（实测：libra 全仓
搜不到 `version=2` / `Git-Protocol`）。

**效果**：`--no-checkout` 的 clone 只需元数据 —— 对象数从 550,013 降到约 10,500，
**约 50×**，且正合 ScorpioFS 的用法（文件内容由 MST/2 按需加载）。

**风险**：中。需要在 v0 路径加 `filter` 解析，涉及协议解析改动。

### 方案 C：pack 产物缓存（L2，设计过未实现）

键 = `commit_oid`。重复 clone → 一次 GET。
**只帮稳态**，不帮首次；实现量较大。**排在 A/B 之后。**

## 明确不做的

- **继续调并发** —— 16 倍扫描已否定
- **给 rustfs 加资源** —— `set resources` 会重启 pod，而它是 `emptyDir`，
  **会清空全部对象**（本轮已因此丢过一次数据）

## 实施顺序

1. 等构建完成 → 部署（含 walk-abort 修复）→ 验证 clone 恢复
2. 重新播种 50k fixture
3. **测方案 A**：让客户端用 `have` 走增量路径，量化第二次 clone 的降幅
4. 若 A 的收益不足，再评估 B 的 v0 filter 实现
