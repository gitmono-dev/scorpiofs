## 判定标准

### 修订记录（2026-09-30，依据实测）

**W1 原为「就绪比 ≤ 0.2」——已修订。** 实测证明等深口径下它**数学上不可能达成**：
双方都需要几乎相同的元数据（路径 + OID，来自 tree），不存在数量级差异。
等深实测 git 6.77 s vs mono 14.88 s（git 快 2.2×）。原来的 0.174 是用
**全量 git ÷ shallow mono** 得到的，口径不可比，已作废。

**修订后的判据**：

| # | 判据 | 门槛 | 理由 |
|---|---|---|---|
| **W1** | **全量口径下不慢于 git** | mono ≤ git × 1.5 | 等深下 git 本就更快；只要求全量口径持平（当前 72.0 vs 72.1 ✅） |
| **W2** | **多工作区边际成本** | **主要判据** | 这才是架构差异所在：每视图真实落盘 ≤ 0.2 × git |
| **W3** | **日常操作不退化** | mono 的 status/add/commit ≤ git 的 3× | 未测完 |
| **W4** | 不依赖 shallow 才能成立 | 全量 clone 必须成功 | 当前 ✗（服务端 ~65s 未定位） |

**关于 W2 的两种口径（都必须报告）**：

| 口径 | 含义 | 门槛 |
|---|---|---|
| 真实落盘 | daemon upper 增量 ÷ 5 | ≤ 0.05 × git |
| 呈现大小（最保守） | 工作区可见字节 ÷ git | ≤ 0.2 × git |

实测：真实落盘 **0.0012**、呈现大小 **0.16** —— **两种口径都通过**。
但必须一并说明**代价**：mono 工作区的内容不在本地，读取要过网络。
W2 省下的磁盘是用读延迟换来的。

### 诚实性约束（写进结论，不许省略）

**mono 不是"全面更快"。** 实测显示的是**一个取舍**：

- 单工作区就绪：**git 更快**（等深 2.2×）
- 多工作区磁盘：**mono 完胜**（约 800× 真实落盘）
- 多工作区耗时：**git 更快**（1.6×）

**结论必须写成取舍，不能写成"mono 优于 git"** —— 除非按使用场景限定
（例如"N 个工作区的 CI 并发场景下 mono 有数量级优势"）。

**最终可辩护结论（W1–W4 全部有数据）**：
1. **多工作区：数量级磁盘优势（约 800×）** —— 架构性
2. **单工作区就绪：filter 口径下与 git 持平**（clone 6.4× 加速）
3. **日常 status/add：比 git 快 5–8×**（upper 层启发式兑现）
4. **commit：比 git 慢 600×+ 且行为不确定（rc=128/rc=0 不稳定、成功后 status 仍报 modified）**
   —— 明确的短板，是后续优化的第一目标
5. **filter+attach 集成缺口**：filter 克隆后 attach 失败（populate 仍读本地 blob），
   最后一公里待做

### R1 成果（已验证）

`git-upload-pack` 首字节 **81.28 s → 0.0014 s**。libra 的 60 s idle 超时不再被触发
（失败形态从"发不出请求"变成"读不到完整响应体"）。总耗时 82.9 s → 66.8 s。

### R2 进展：用阶段分解而非猜测定位

给 `traverse` 加 per-directory 计时后（10,479 个目录聚合）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| **DRAIN**（读流+推入编码器） | **57,234 ms** | **99.8%** |
| OPEN（拿到流） | 137 ms | 0.2% |
| TREES | 9 ms | ~0% |

**并发扫描（64/256/512/1024）完全无效** —— 16 倍并发，耗时 56.0→56.5 s 不变。
**CPU 实测**：89.5 s CPU / 64 s 墙钟 = 1.4 核（限额 4 核）→ 既非纯等待、也非 CPU 饱和。

**定位到具体函数**（`drain` 中每 blob 两次拷贝之一）：

```rust
// git-internal hash.rs
pub fn from_type_and_data(object_type, data: &[u8]) -> ObjectHash {
    let mut d: Vec<u8> = Vec::new();
    ...
    d.extend(data);          // ← 把整个 blob 再复制一份去算 hash
    Self::new_for_kind(...)
}
```

而**四行之上的文档**就写着替代方案："`from_type_and_data_for_kind`，
**streams the header instead of copying the payload**"。

已改为流式版本（`e653e69`），并顺带修掉一个隐患：`Blob::from_content_bytes`
从 **thread-local** 取 hash kind，而 async worker 上未设置 —— 新代码显式传入
`self.object_hash_kind()`，不再依赖环境状态。

**待验证**：构建中，将测 drain 与总耗时是否下降，以及 hash 占 drain 的实际比例
（新的 `hash_ms`/`hash_calls` 日志会直接给出）。

### 流程教训（已生效，写进规则）
